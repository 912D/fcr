# 如何写一个规则包

> 目标：把一个领域的"开跑前检查清单"写成可执行、可审计、可替换的 JSON。

## 0. 先定性质：你写的是**检查表**，不是模型

规则包回答三个问题：**缺什么、有什么红旗、先做哪一步。** 如果你的规则需要"跑一遍数据才知道"，它不该在这里——这里只有"看任务描述就能判断"的规则。

## 1. 从失败模式出发，不从模型出发

错误写法："表格数据 → XGBoost"（这是模型推荐）。
正确写法："同批次样本跨集 → 批次效应被当成模型能力 → 需按批次整组切分"（这是失败模式）。

判断标准：这条规则**能不能在训练之前**判断？能，才写。

## 2. 字段字典

```json
"fields": {
  "sample_unit": { "type": "enum", "values": ["molecule", "cell", "batch"], "description": "一个样本与独立单位" }
}
```

要求：

- 每个被条件引用的字段都要声明；
- 枚举必须给 `values`（校验器会用）；
- 字段越多，填写成本越高——**优先控制在 10–15 个**。

## 3. 缺项门控（priority 1–9）

每个必填字段一条，条件是 `state.get('字段') is None`，动作是 `append_once missing_inputs`。缺项不清，后面的红旗与候选都没有意义——这是优先级分段的理由。

## 4. 红旗（priority 20–39）

每条红旗对应**一个**已知失效模式，动作通常是两条：

1. `append_once red_flags`：说清"错在哪"；
2. `append_once required_checks`：说清"先做什么"。

并写 `evidence`：

```json
"evidence": { "kind": "literature", "note": "组泄漏", "source": "Kapoor & Narayanan 2023" }
```

`heuristic` 必须写"未校准"。

## 5. 候选（priority 60–69）

只给**模型族**，不给排行榜；每族一句"为什么"。

## 6. 结论（priority 90–99）

固定三条，按序：

1. 有缺项 → `信息不足`；
2. 有红旗 → `有红旗：先处理`；
3. 都没有 → `可进入基线`。

条件写成 `state.get('missing_inputs') is None and ... and state.get('verdict') is None`，动作用 `set_default`（幂等）。

## 7. 校验与试跑

```bash
node cli/fcr.mjs validate packs/<你的包>/pack.json   # 必须是 0 error
node cli/fcr.mjs run --pack packs/<你的包>/pack.json --data packs/<你的包>/data.example.json
node cli/fcr.mjs explain --pack packs/<你的包>/pack.json --data packs/<你的包>/data.example.json
node --test
```

试跑数据至少两条：一条"该红"，一条"该绿"。**你期望的结论写进 `_expected` 字段**，测试会对照。

## 8. 提交前清单

- [ ] 所有规则有 `evidence`，`heuristic` 标了"未校准"；
- [ ] 每条红旗都能指向一个具体的失败模式；
- [ ] 示例数据能触发每条红旗（至少一次）；
- [ ] `validate` 零错误；
- [ ] `node --test`（在仓库根目录）全绿；
- [ ] README 写清适用域与边界。

## 9. 常见错误

| 错误 | 后果 | 修正 |
|---|---|---|
| `params.key` 不加引号 | 写入位置错误 | `"'red_flags'"` |
| `set_field` 无守卫 | 反复触发到 `max_iter` | 条件加 `state.get('字段') is None` |
| 条件里写 `===` / `&&` | 解析失败 | 用 `==` / `and` |
| 同一轮想触发多条 | 只触发一条 | 拆成多条顺序规则 |
| 用 `append_once` 写标量 | 变成列表 | 用 `set_field`（带守卫）或 `set_default` |
