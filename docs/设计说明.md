# 设计说明：为什么是"规则包 + 确定性引擎 + LLM 起草"

## 一句话

**生成与裁决分离**：LLM 负责把领域知识写成候选规则，引擎负责判定，校验器负责检查格式与陷阱，人负责最终签字。概率性生成不进入判定链。

## 三个角色

| 角色 | 能力 | 不能做什么 |
|---|---|---|
| LLM | 把一段自然语言经验转成 `{rule_id, condition, actions}` 草稿 | 不能判定、不能执行、不能直接写结论 |
| 引擎 | 确定性前向链：同一输入永远同一输出；每一步可追 | 不能生成知识、不能"猜"缺失字段 |
| 校验器 | 结构检查、条件解析、守卫检查、引号陷阱检查 | 不能判断规则是否正确——只能判断它是否**合法** |

## 为什么不用 LLM 直接给结论

1. **不可复现**：同输入两次回答不同，结论无法写进实验记录；
2. **不可审计**：失败了找不到"哪一步错了"；
3. **不可定责**：安全/医疗/材料场景，结论要能追到依据；
4. **可被提示词污染**：结论随提问方式变化。

规则包把"知识"变成**可版本化的数据**：改一条规则就是一次有 diff 的提交，而不是一次无法复现的对话。

## 为什么规则包要带 evidence

一条规则若没有来源，它只是**意见**。`evidence.kind` 把意见分为四档：

- `heuristic`：经验，未校准——**只能当提醒**；
- `standard`：领域共识做法；
- `literature`：有文献支持；
- `calibration`：用数据校准过（**本仓库目前没有一条达到这一档**）。

这个分层是防止"把意见伪装成事实"的最低成本手段。

## 为什么冻结引擎语义

规则包是数据，引擎是解释器。解释器一旦漂移，所有历史结论都失去可比性。因此 `spec/00-格式规范.md §7` 的裁决语义（排序、单轮单条命中、stable 集、`max_iter` 截断）属于格式的一部分，**改动即破坏兼容**。

## 已知的架构缺口（v1 之后）

1. **没有闭环**：规则触发后没有和真实结果对账（红旗是否真的预示失败？）。需要"结果日志 + 规则精度"的评测；
2. **覆盖率未知**：39 条规则覆盖多少真实失败模式，没有测量；
3. **没有残差报告**：批量跑完只给汇总表，没有把"无规则命中/提前 no_match/缺失字段"聚成清单——而这份清单才是"发现新因素"的入口；
4. **规则包之间不可组合**：一个任务只能用一个包。若要做"基础包 + 领域包"的分层，需要 `extends` 机制（v2）。

这四条是设计上的**已知缺口**，不是待修 bug。写进文档是为了让使用者知道边界在哪。
