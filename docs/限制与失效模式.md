# 限制与失效模式

> 读这一页比读 README 更重要。**FCR 是检查表，不是神谕。**

## 1. 它不是预测器

它不估计任何数值，不预测成功率，不给出"这个方案能不能成"。它只检查**方法前提**：缺什么、有什么已知红旗、先做哪一步。最终判断必须由验证（实验、交叉验证、复现）给出。

## 2. 规则是意见，不是定律

`evidence.kind = heuristic` 的规则（本仓库大多数）是**经验**，且明确标注"未校准"。典型例子：

- `N < 100 不上大模型`——阈值来自工程经验，不同问题的临界值不同；
- `缺项优先于红旗`——是规则包的设计选择，不是物理定律；
- `多协议混用 = 不可比`——通常成立，但若显式建模协议效应则未必。

把 `heuristic` 当 `calibration` 用，是这个工具最常见的误用。

## 3. 没有闭环

规则触发之后，没有与真实结果的对照。**"红旗"是否真的预示失败，本仓库没有数据证明。** 因此：

- 不要用红旗数量当项目风险评分；
- 不要用它做资源分配；
- 若要做闭环，需要"项目结果日志 + 规则精度统计"（见 `设计说明.md` 已知缺口）。

## 4. 覆盖率未知

39 条规则覆盖多少真实失败模式，没有测量。它更像"常见坑清单"，而不是"完备检查表"。

## 5. 条件语言是子集

条件是 **Python 风味子集**（`state.get('x')`、`and/or/not/in/is`），**不是 JavaScript**。不要写 `===`、`&&`、`||`、`!`、`?.`。写错时校验器会报"条件解析失败"。

## 6. 单条命中

每轮只触发一条规则；若需要"同一轮执行多条"，请拆成多条顺序规则。这不是缺陷，是冻结的语义（保证可追溯）。

## 7. 参数绑定的坑

`params.key` 必须带引号（`"'red_flags'"`）。不带引号会被解析为字段引用 `state.red_flags`，导致写入位置错误。校验器将其列为错误。

## 8. 不该用的场合

| 场合 | 为什么 |
|---|---|
| 需要统计推断（显著性、置信区间、因果） | 它不做统计 |
| 需要预测性能评估（AUC、RMSE、校准曲线） | 它不跑模型 |
| 安全定责、医疗决策、法律结论 | 红旗不能替代人审与验证 |
| 数据本身严重缺失 | 缺项门控只会反复告诉你"信息不足" |
| 需要跨包组合的判断 | v1 不支持 `extends`，一个任务只能用一个包 |

## 9. 与标准方法的关系

它**不替代**：交叉验证、数据划分、校准、AUC/PR、适用域分析、不确定性量化。它只负责在开跑之前提醒你"这些事得做"。
